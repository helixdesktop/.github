# Contributing to Helix

Thank you for helping. This guide applies to every repository in the
[helixdesktop](https://github.com/helixdesktop) organization unless a
repository has its own `CONTRIBUTING.md`.

## Where things go

- **New features** are written up in [spec](https://github.com/helixdesktop/spec)
  first and implemented afterwards.
- **Bugs** are reported in the repository the problem is in.
- **Security problems** are reported privately, never in a public issue; see
  [SECURITY.md](SECURITY.md).
- **Translations**: corrections and reviews by native speakers are especially
  welcome; each repository's `TRANSLATING.md` (or, for the website, its
  README) explains how.

## AI-assisted contributions are welcome

You are welcome to use AI tools (coding assistants, agents, machine
translation) for code, documentation, specs, translations and issue
reports. Much of Helix itself is written with them.

The same standards apply as for any other contribution:

- **You are responsible for what you submit.** Read it, understand it, and
  be ready to explain and change it in review.
- **Test it.** Build it, run the tests, and try the change itself where
  that is possible. Say what you could not check.
- **Say that a tool helped**, for example with a `Co-Authored-By:` line in
  the commit message or a note in the pull request. It doesn't change how
  the contribution is judged; it helps reviewers know what to look at.
- **Keep it focused.** One change per pull request, sized to be reviewed.
  Don't open large numbers of generated issues or pull requests that
  nobody has checked.
- **Only submit what can be released under CC0** (see below): nothing
  copied from code under another licence, whoever or whatever produced it.
  Helix is a clean-room implementation, so don't paste in GNOME's source.

Machine translations are acceptable for a language's first version as long
as they are marked as unreviewed.
